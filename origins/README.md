# origins — 送信元ドメインの公開台帳

メールの送信元ドメインについて分かっていることを EDN で公開する。良性側と不正側を
**同じ repo の別ファイル**に置く。1つのドメインを調べる人が2箇所を見なくて済むように。

| ファイル | 中身 |
|---|---|
| `origins.edn` | ドメインが何であるか、どこに振り分けるか、何をしてよいか |
| `abuse.edn` | 迷惑・詐称・不正の観測と判定、および**偽陽性の記録** |

## origins.edn — 3つのフィールドは別のことを言っている

```clojure
{:origin/domain "notify.cloudflare.com"
 :origin/registrable "cloudflare.com"
 :origin/kind :infrastructure        ; 何者か
 :route/projects ["infra"]           ; どこに振り分けるか
 :trust/level :self-registered       ; 何をしてよいか
 :trust/evidence [...]
 :observed/messages 39}
```

`:origin/kind` と `:route/projects` と `:trust/level` を1つにまとめない。**この3つは
食い違う** —— 銀行は重要だが定型、ニュースレターは軽いが未検証で、まとめると片方の
答えが消える。

## trust は件数から推論しない

あるドメインから400通届いたことは、そのドメインが名乗るとおりの相手かどうかについて
**何も言っていない**。`:trust/level` は `:unverified` から始まり、
`:trust/evidence` に根拠が入ったときだけ動く。

計算できる根拠が1つだけある。**Apple のプライベートリレー経由で届いたメールは、
所有者がその相手のために作った宛先に届いている** —— これは同意であり、
`:self-registered` として記録する。`:trusted` ではない。「自分で登録した」ことと
「送られてくる内容を信用する」ことは別の主張だから。

| level | 意味 |
|---|---|
| `:abusive` | 不正の証拠がある |
| `:suspected` | 疑いの観測がある（判定ではない） |
| `:unverified` | 既定。何も分かっていない |
| `:self-registered` | 所有者がこの相手に宛先を発行した |
| `:trusted` | 人が根拠付きで信用すると決めた |

trust が門になるのは **capability** の側面: 未検証の送信者の本文は
**モデルのコンテキストに入れない**（メールは指示ではなく、未知の相手が指示を書ける
状態を作らない）。これは新しい規則ではなく、ADR-0016 が messenger に対して既に
引いている線をメールでも使っているだけ。

## abuse.edn — 偽陽性こそが資産

2026-08-06 時点、実受信 1,127 通・166 ドメインから **フィッシングは0件**。
検出できなかったのではなく無かった。

代わりに記録してあるのは**引っかかった正規メール**で、これが後から規則を書く人に
一番役に立つ:

- `ftx.com` —— 破綻した取引所を名乗るが、FTX Recovery Trust は実在の破産財団で
  配当は実際に進行中。「破綻企業を名乗る = 詐欺」は成り立たない
- `vpass.ne.jp` —— 表示名「三井住友カード」がドメイン文字列に含まれないだけ。
  日本語表示名とラテン文字ドメインは原理的に一致しない
- `1password.com` —— パスワード管理サービスなので件名に「パスワード」が入って当然

**件名に「認証」「至急」「お支払い」が含まれることは、詐称の証拠にならない。**
正規のメールこそがその語を使う。

## 詐称判定は受信サーバーの判定を使う（2026-08-07 に開通）

2026-08-06 版のこの節は「認証ヘッダを保存していないので詐称の機械判定が原理的に
できない」と書いていた。**それは解消した。**

答えは賢いヒューリスティックではなく、**受信サーバーが既に計算した結果を捨てないこと**
だった。Gmail は送信者が制御できない DNS で SPF/DKIM/DMARC を判定し、
`Authentication-Results` に書いている。3ヘッダだけ保存する。

**DMARC がヒューリスティックの届かない検査。** フィッシングは攻撃者が持つドメインで
SPF も DKIM も通せる。DMARC はまさに「その2つと From: が一致するか」を見る。

```
実コーパス 1,151 通 / 174 ドメイン
  authenticated              1039
  unaligned                    36   ← 転送・メーリングリスト。告発しない
  impersonation-suspected       0
  unknown                      76   ← ヘッダ保存前。pass に格上げしない
```

**`:unknown` を pass に格上げしない**のが一番大事な性質。証拠が無いのに
「認証済み」と答える台帳は、置き換えたヒューリスティックより悪い —— あちらは
少なくとも不確かに見えた。

**`:unaligned` は告発ではない。** 転送とメーリングリストは常に alignment を壊す。
この36件には**自分のドメインからの転送と、法務・不動産のやり取り**が含まれている。
「疑わしい」に畳んでいたら全部誤検知だった。

残る穴は `abuse.edn` の `:gaps` に1つ:
本文中のリンクを抽出していないので、**表示 URL と実リンク先の不一致**は未検出。

## 認証は事実であって信用ではない

`origins.edn` の各ドメインは `:observed/authentication` を持つが、これは
`:trust/level` を動かさない。**DMARC が通ることは「名乗るとおりの相手である」
という意味で、「信用に値する」とは別の、はるかに狭い主張** —— 検証済みのスパマーは
検証済みである。

記録する理由は1つだけ: **一貫して認証を通すドメインを名前で指した規則は、
そのドメインを騙る相手に欺かれない。** 規則が文字列への当て推量ではなく、
裏に検査を持つものになる。

## 生成

`origins.edn` の観測部分は受信から生成され、分類部分は人が書いたものが保持される。
件数と日付は毎回上書きされる —— そうしないとファイルが「もう存在しないメールボックス」
を記述し続けるため。
